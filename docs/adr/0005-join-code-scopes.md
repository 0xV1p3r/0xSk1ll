# Join codes grant a scope: the whole fleet or only the machine itself

Every joined machine used to manage the whole fleet. That suits one person's machines, but not a shared or less trusted machine, such as a CI runner or a colleague's laptop. A join code now grants one of two scopes, stored per machine at the server and checked in every handler:

- `fleet` (the default, and what every machine had before) may create join codes, change any machine's assignment, undo any log entry and remove any machine.
- `self` may change only its own assignment, undo log entries for itself (whoever wrote them) and remove itself. It may not create join codes, so it can't mint a `fleet` code for itself or anyone else.

Every machine may still read the fleet view, every assignment, the log and the imports view. The admin token keeps full rights. A machine that is removed and joins again gets the scope of its new code.

A `self` machine may remove itself. Leaving touches only its own assignment and token, the log keeps a record, and coming back needs a new code from a `fleet` machine or the admin. It lets a machine be retired from that machine without granting anything over the others.

## Consequences

- Scopes cover fleet administration, not content. A `self` machine can still push to the server, and every machine pulls the baseline it pushes, including changes to skills that are on elsewhere. Scopes don't make an untrusted machine safe to join.
- A push used to drop every machine's toggles for every item missing from the new baseline. A `self` machine's push would then change other machines' assignments, and putting the content back wouldn't bring them back. A push now drops toggles only for the items it removed (in the HEAD before it, not after), keeping each machine's toggles for items in its draft or unpushed commits: on every machine for a `fleet` machine or the admin, and only on its own assignment for a `self` machine. Rejecting such pushes would have kept a `self` machine from removing its own content whenever anyone else had it on, and recording which items to keep (an earlier design) still lost toggles and grew without bound. The cost is toggles for absent items, which do nothing until an item with the same kind and name returns, and which a `fleet` machine or the admin can clear. Nothing records cleanup still to do: if it fails, or the server stops before it runs, the toggles just stay, which is the safe direction. Startup never sweeps.
- That cleanup is only as right as the trees it diffs, so the server reads each commit's tree as it is. Pushes may update only the baseline branch, so a machine can't push `refs/replace/*`, tags, other branches or refs under the branch's own name, and every server-side read ignores replacement objects (also set in the repo's config on every start). The server decides the baseline branch once at startup, after creating the initial commit: HEAD must name a branch under `refs/heads/`, or the server refuses to start and says how to fix the repo. `receive.hideRefs` and a pre-receive hook that the server writes over on every start both refuse every other ref. Changing the repo's HEAD takes a restart. Replacement refs already in a repo are ignored and logged at startup, not deleted. The server stores a commit's items only with that commit, and lists the commit before a push again by id when it doesn't have it. A draft discard reads the branch itself, under the push lock, rather than the HEAD cached after the last push. A HEAD read is a commit, an unborn branch (checked: the branch doesn't exist) or an error, never an error taken for an empty tree. If HEAD can't be read after a push, or a backend's shutdown can't be confirmed, the cached HEAD is marked stale until it is read again. If a needed read fails, times out, or writes more than 64 MiB, the push drops nothing, and a draft discard drops nothing and closes the daemon's session with code 1013 (try again later), so the daemon reconnects with growing backoff and sends its unacknowledged discards again. Each read has a deadline, each push and each discard a total budget for its reads, and a read that misses either, or whose caller goes away, is stopped with its children. The reads the server makes while setting up the repo at startup run without that deadline.
- Scope is checked again inside each write's database transaction, from the token the request came with, so a request authenticated before its machine was removed, or joined again with a narrower scope, can't act with the old rights. A push is attributed by its token, never by machine id. It checks its token again once it holds the push lock, before receive-pack starts, and removing a machine takes that lock too, so a removal happens either before a push starts (which is then refused) or after it and its cleanup are done. The removal keeps the lock until its database work commits, even if its request goes away first. A pusher whose token is gone by cleanup sweeps nothing. A daemon session registers, after checking its token, under the same database lock as a removal, and a removal revokes only the session holding the removed token, so neither a delayed old upgrade nor a late revocation can end a rejoined machine's session.
- Existing machines and unused join codes migrate to `fleet`, so upgrading changes no machine's permissions until someone creates a `self` code. Cleanup does change for every machine: it only ever drops toggles for the items a push removed, so a push now keeps toggles for items that were already absent before it, where an older server dropped them on any push. The cleanup-failure and ordering guarantees above rely on the server reading trees as they are, never diffing a commit it didn't list or sweeping against a HEAD it didn't just read, bounded reads, and removals holding the push lock until they commit. A repo whose HEAD is detached or outside `refs/heads/` now stops the server from starting, where an older server served it and took pushes to `main`.
- The protocol change is additive: an older daemon sends no scope and gets a `fleet` code. A newer client checks the scope in the response, because an older server ignores the request's scope and grants `fleet`.
- Two scopes only. Finer rules (per harness, per item, read-only machines) would need roles, which we don't need yet.
